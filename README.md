# 九九バトル

小学 2 年生が、学校で九九が始まる前に全部言える状態になることを目的とした PWA。

報酬をアプリの中に置かない。教室で「これ知ってる」となる体験を報酬とする。
設計の方針と判断の根拠は `docs/design-notes.md` を参照。
ストーリーモードの設計と判断の根拠は `docs/story-mode-design.md`。
ランクと見た目の判断は `docs/rank-design.md`。
子どもが話を注文する仕組みの判断は `docs/story-authoring-design.md`。
話の追加手順は `docs/story-prompt.md`（親が LLM に投げる雛形）。

## 設計上、意図的にそうしている点

実装を変更する際は以下を壊さないこと。いずれも設計メモ上の判断に対応する。

- **間違いで減点しない。** ライフ、連続正解、赤い×は持たない。
  誤答は出題の重み（`lib/kuku.ts` の `weightOf`）にのみ反映する。
- **タイマーは考えている時間だけを測る。** 誤答時の解説中は計測を止める。
  間違いが記録を悪化させると、減点しない方針と矛盾するため。
- **連続日数とプレイ時間を記録も表示もしない。** 途切れた日に開かなくなる理由を作らない。
- **苦手を子どもに見せない。** 段ごとの遅さと誤答率は親画面にのみ表示する。
- **解放は 1 段ずつ。** 未習の段を出すと「わからない」だけが残る。
  既定の順序は 1 から 9 の数字順だが、学校の進度に合わせて親が並べ替える。
- **1 回 10 問。** 物足りないくらいの長さに保つ。
- **ポイント・コイン・ガチャを置かない。** 見た目の解放を追加する場合も、
  達成と無関係な配布にはしないこと。
- **付かないランクを作らない。** 10 問終えれば必ず「クリア」が付く。
  「ランクなし」は不合格の別名であり、減点しない方針と衝突する。
- **ホームの「はじめる」を画面の外に出さない。** 外枠は画面の高さに固定し、
  あふれるのは中身だけにしてある（`.app[data-fit]` と `.scrollArea`）。

## 外装について

角を斜めに落とした HUD（アーケード筐体の読み方）で統一している。
判断の根拠は `docs/rank-design.md` の判断 7。

- **ゲーム感はフォントで出さない。** ドット絵フォントは使わない。
  形（`clip-path` による切り欠き）・発光・地の質感・量の刻み方で出す
- **色はすべてテーマ変数から導出する。** 外装は全テーマ共通で、色だけが
  テーマから来る。既定は `arcade`（シアン）だが、緑・紫・青でも成立する
- **量は刻む。** 体力と進度は 1 本の帯ではなく枡に割る。
  帯の長さは「どれくらい」しか伝えないが、枡は「あと何個」を伝える

触るときに踏みやすい点が 3 つある。

- **`clip-path` は `box-shadow` を切り落とす。** 角を落とした要素の外側の光は
  `filter: drop-shadow()` で出すこと
- **地の層（`body::before` / `body::after`）は `z-index: 0`、中身は `1`。**
  `body` に不透明な背景を戻すと地の格子が隠れる（描画順の問題）
- **小さい箱に大きな切り欠きを使わない。** `.panel` の切り欠きは 14px ある。
  答えの札のような小さい箱には `.factCell` のように専用の値を持たせる

## ランクについて

タイムでゴールド・シルバー・ブロンズが付く。判断の根拠は `docs/rank-design.md`。

- **目標は段ごとに違う。** 全段を同じ秒数で測ると、1 の段は必ずゴールド、
  9 の段は一生ゴールドなしになる。1 問あたりの目標を
  固定費・桁数・積の大きさから組み、10 問ぶんを合計している（`src/lib/rank.ts`）
- **ゴールドは全問正解のときだけ届く。** 速いだけで取れると、
  覚えずに連打した方が速くなる。落とした数だけ上限が下がる
- **10 問終えれば必ずランクが付く。** 最低は「クリア」
- **見せるのは 1 つ上までの差だけ。** 下位の子にゴールドまでの距離を出すと、
  それは苦手の通知になる
- **厳しさは親が 1 段ずらせる。** 実際の速さは遊ばせるまで分からない

ブロンズの境目が 1 分を超えないことは単体テストで固定してある。
「1 回 1 分で終わる長さ」をランクの境目が壊さないため。

## 画面の高さについて

ホームは外枠を画面の高さに固定し（`.app[data-fit='true']`）、
あふれる可能性があるのは中身（`.scrollArea`）だけにしてある。
開いて最初に押す「はじめる」が画面の外に出ないことを構造で保証するため。

画面の高さに応じた圧縮を 3 段（790px / 620px / 580px 以下）置いている。
**レイアウトを変えたら 1 つの画面サイズで確かめて終わりにしないこと。**
320×568 から 430×932 までで、次が崩れていないことを確認する。

- 文書がスクロールしない
- 「はじめる」が全体見えている
- 段カードが全部見えている
- きろくの 2 行とも見えている
- 見切れている要素が無い

目視では分からないので `npm run layout-check` で測る。

```bash
npm run build && npm start -- -p 3210 &
npm run layout-check
```

崩れていたら終了コード 1 と、どのサイズでどの条件が落ちたかを出す。
Chromium の場所が違う場合は `CHROMIUM_PATH` で指定する。

## 子どもが話を注文する仕組み

**このアプリで刺さったのは「話を読むこと」ではなく「話を作らせること」だった。**
実機で確認したところ、同梱の話は使われていなかった。元々 AI に話を作らせて遊んでいた子なので、
楽しんでいたのは注文する側であって、出来上がったものを読む側ではなかった。

設計メモは最初からそう書いていた。

> 報酬は「話の続きが読めること」ではなく「自分の考えた世界が動いていること」。

判断の根拠は `docs/story-authoring-design.md`。

### 流れ

```
子どもが注文する  →  Supabase に残る  →  親の Claude が作る  →「ぼうけん」に並ぶ
   （アプリ）        （status: ordered）   （スケジュールタスク）  （status: ready）
```

**LLM を API として呼ばない。** 話を書くのは、スケジュールタスクを実行している
Claude 自身である。Anthropic の API は従量課金で、claude.ai のサブスクリプションとは
別請求になる。子どもが注文するたびに課金される構造は、家庭用のアプリには重い。

アプリ側は注文を置くだけで、生成には一切関わらない。生成を叩ける URL も存在しない。

### 設計上そうしている点

- **検査は両側でかける。** 書き手の側は `publish` が検査に通らなければ書き込まない。
  読む側（アプリ）も読み込んだ話を毎回検査し、通らないものは遊べる一覧に出さない。
  Supabase は手でも触れる以上、壊れた話が子どもの画面に出る経路を残さない
- **id・段・作者はモデルに決めさせない。** こちらが知っている事実であって、創作の対象ではない
- **親の確認は事後。** 即時性がこの仕組みの核。親画面から一覧を見て消せる
- **未習の段の話は注文できない。** 自分で選んだ分、分からなかったときの落差が大きい
- **1 日の本数に上限（3 本）。** クライアントと処理側の両方で効かせる
- **プロンプトは `docs/story-prompt.md` から実行時に読む。** 親が手で LLM に投げるときと
  同じ文面を使う。二重に持つと必ず片方が古くなる
- **失敗を黙って消さない。** 作れなかった注文は `failed` として残し、
  子どもの画面に「うまく できなかったみたい」と出す。
  注文が消えたように見えると、次を注文しなくなる

### 有効にする手順

1. `supabase/schema.sql` を実行済みであること（まだなら先に実行する）
2. `supabase/schema-stories.sql` を SQL エディタで実行する
3. `.env.local` に `FAMILY_CODE`（親画面で設定した合言葉）を足す
4. `docs/story-task.md` の「タスクに渡す文面」で Routine を作る。
   親が手で動かしたいときも、同じ文面を投げればよい
5. 親画面の「作る時刻」に、仕掛けた時刻を入れる
   （子どもの画面に「つぎに できるのは ◯じごろ」と出すためだけのもの）

手順の詳細と、書き手が守ることは `docs/story-task.md`。

## モードについて

ホーム上部で「たたかう」と「ぼうけん」を切り替える。画面遷移ではなく中身の入れ替えにしてあるため、
「はじめる」までのタップ数は増えない。選んだ側は端末に覚えさせ、次に開いたとき同じ側から始まる。

動機の構造が違うため、2 つを統合しない。

| | 動機の源 |
| --- | --- |
| たたかう | 親の記録を抜くこと |
| ぼうけん | 自分の作った世界が動いていること |

片方が刺さらなくても、もう片方が残る。

### 散策の作り

骨組みは固定で、中身だけが毎回引き直される。

```
街 → 道をえらぶ → 場面 → 出会い(戦い) → 場面 → 出会い(戦い) → 街へ帰る
```

骨組みを固定するのは 1 ループの長さを保つため。ここが可変だと、日によって 1 回の長さが変わる。
中身を引くのは組み合わせで増やすため。場面を 1 つ足すだけで通り数が増える。

直近に出たものは次の散策で避ける。組み合わせがあっても、同じ相手が続けて出ると「また同じ」に感じられる。

### ストーリー中の戦いの扱い

- **ベスト記録には並べない。** 時間を競っていないため、混ぜると親子の記録比べが成立しない
- **習熟度には積む。** どちらで解いても覚えたことに変わりはない
- **未解放の段の話は出さない。** 話だけ先に進むと、段を 1 つずつ解放している意味が無くなる
- **進行は端末ごとに持ち、同期しない。** 親の端末で先へ進められると意味が壊れる

## 音声について

問題は平読み（「ろく かける なな」）、答えは九九の唱え方（「ろくしちしじゅうに」）で読み上げる。
唱え方は覚える対象そのものなので、誤答時と結果画面のタップ時にのみ再生する。
読みのテーブルは `src/lib/yomi.ts` にある。

iOS Safari では最初の発話がユーザー操作起点である必要があるため、
「はじめる」のタップ時に `primeSpeech()` を呼んでいる。

## テーマの追加

`src/data/themes/` に JSON を置き、`src/lib/themes.ts` の `THEMES` に追加する。
外装は共通なので、足すのは色と文言と敵だけでよい。
問題文の着せ替えは LLM で生成してよいが、生成結果は JSON として保存し、実行時には呼ばない。
応答速度と費用の両面で、毎回呼ぶ形にはしないこと。

敵の名前は親画面から編集でき、その場で反映される。
子どもに決めてもらうための項目であり、この用途を想定して即時反映にしている。

## 親が自分の端末を使う場合

Supabase を有効にすると、記録と共有設定が端末間で同期される。
設定しない場合は端末内（localStorage）で完結し、親は子の端末の親画面から記録を作る。

### 手順

1. Supabase プロジェクトを作り、`supabase/schema.sql` を SQL エディタで実行する
   （中身はすべて冪等なので、更新があれば何度流し直しても安全）
2. 環境変数を設定する

   ```bash
   cp .env.example .env.local
   # NEXT_PUBLIC_SUPABASE_URL と NEXT_PUBLIC_SUPABASE_ANON_KEY を設定
   ```

3. 親子それぞれの端末で、親画面の「べつの端末とつなぐ」に**同じ合言葉**を入れる
4. 親の端末では「この端末は」を「おうちのひとの端末」に切り替える

### 同期するもの / しないもの

| 種類 | 例 | 同期 |
| --- | --- | --- |
| 記録 | タイム、正答数、問題ごとの結果 | する |
| 共有設定 | 段の解放、テーマ、敵の名前、呼び名 | する |
| 端末設定 | 合言葉、この端末の持ち主、音声の ON/OFF | **しない** |
| ストーリー | 場面、あいて、セリフ | しない（静的 JSON） |

合言葉と持ち主を同期させると意味が壊れる。
親の端末の設定が子の端末へ流れてきて、子どもの記録が親のものとして残る事故になる。

### 設計上そうしている点

- **端末内が常に正。** リモートは相手の記録を取りに行く鏡として扱う。
  通信が落ちていても最後まで遊べ、記録は端末に残って次回の同期で送られる
- **記録は書き換えない。** 再送による重複はサーバ側で無視させ、`update` 権限を渡さない
- **共有設定は後勝ち。** 更新時刻の新しい方を採る。家庭内で同時に触ることは稀
- **anon キーは公開されるものとして扱う。** 家族ごとの分離は RLS とリクエストヘッダ
  `x-family-code` で行う。合言葉は推測されにくい長い文字列にすること

### 確認できていること

- 実プロジェクトに対してスキーマを適用し、記録が同期されることを確認した
- 接続できない状態でも 1 回分を遊びきり、記録は端末に残ることを確認した

### 有効化したあとに必ず確かめること

**同期が成功することと、他人から守られていることは別である。**
RLS が効いていなくても、正しい合言葉での同期は成功してしまう。

片方の端末の合言葉をでたらめな文字列に変えて、
**相手の記録が見えなくなること**を確認すること。
見えたままなら RLS が効いていない。`supabase/schema.sql` のポリシーを流し直す。

合言葉は実質これだけが鍵になる。anon キーは公開されるものなので、
短い合言葉にすると誰でも読み書きできる状態に近づく。

### Supabase のリンタも見ること

Supabase のダッシュボード（Advisors）か MCP の `get_advisors` で、RLS の抜けや
関数の設定を機械的に点検できる。実際、`request_family_code` の `search_path` が
固定されていない指摘が出たため `schema.sql` で `set search_path = ''` を付けた。
この関数はすべての RLS ポリシーから呼ばれるので、ここが緩いと分離の根が緩む。

## 成功の判定

| 問い | 見るもの | 実装 |
| --- | --- | --- |
| 開かれているか | 親が言わずに開いた回数 | 親画面「この 7 日で開いた回数」 |
| 覚えたか | 学校で九九が始まったときに既に言えたか | アプリ外で確認する |
| 態度が変わったか | 九九以外の勉強に対する反応 | アプリ外で確認する |

連続日数やプレイ時間は成功指標にしない。
増やそうとすると子どもの時間を奪う方向に働き、目的と逆行する。
