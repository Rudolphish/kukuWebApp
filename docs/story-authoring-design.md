# 九九バトル 第 4 段階 設計メモ — 子どもが話を注文する

`story-mode-design.md` の続き。ストーリーモードが使われなかった原因と、その直し方の記録。

採用した案と、検討して採らなかった案の両方を残す。理由まで書いておくことで、
後から同じ案を思いついたときに検討をやり直さずに済む。

## 発端

ストーリーモードは実装済み（2 エリア・各 720 通り）だが、実機で使われていない。
理由を本人に確認したところ、次のことが分かった。

> 娘は元々、AI にストーリーを作らせて、それを読むのを楽しんでいた。

つまり楽しんでいたのは **読むこと** ではなく **作らせること** だった。
読むのはその結果にすぎない。

### これは設計メモが既に言っていたことである

`story-mode-design.md` の冒頭にこう書いてある。

> **子どもが作った話が、ゲームになる。**
>
> 報酬は「話の続きが読めること」ではなく「自分の考えた世界が動いていること」。
> 前者はアプリ内に置いた報酬であり、後者は現実の達成である。**この区別が設計全体を分ける。**

そして実装されたのは、2 エリア・各 720 通りの **読むための話** である。
メモが「これではない」と名指しした側を作り込み、
「これである」と書いた側（子どもがアプリから話を追加する画面）を未実装のまま残していた。

720 通りへの拡張も同じ読み違いの上にある。実機で「1 回で遊び尽くされる」と報告を受け、
それをバリエーション不足と解釈して組み合わせを増やしたが、
1 回で終わったのは変化が足りなかったからではなく、**読むこと自体が動機ではなかった**から。

### 親が仲介する形は既に試して刺さらなかった

`story-prompt.md` は、親が LLM に投げて JSON を作り、手で置く手順である。
これは試されたが刺さらなかった。

**この形には、子どもが注文する瞬間が無い。** 子どもから見ると、
出てきた話が built-in の 2 エリアと区別がつかない。種を出した記憶と、
数日後に現れた話が結びつかない。

## 判断 1: 同期生成ではなく「注文 → あとで届く」にする

本人の提案。待ちが発生してよい代わりに、数時間おきのスケジュール実行で生成する。

採った理由は 3 つ。

**API キーを置く場所が 1 か所減る。** 生成がスケジュール実行だけなら、
アプリ側に生成の口を作らなくてよい。Vercel にキーを置かず、
生成を回す場所だけが鍵を持つ。守るべき口が増えない。

**費用の上限が構造で決まる。** 1 回の実行で処理する件数を決めれば、
子どもが注文を連打しても費用は跳ねない。クライアント側の制限は迂回されうるが、
処理側の上限は迂回されない。

**待つこと自体が体験になりうる。** 注文して、あとで届く。
設計メモの柱 4 は「そのアイデアが**翌日には動いている**状態にする」を想定しており、
数時間はその範囲内どころか、かなり速い側である。

### 残るリスクと、その切り分け

親が仲介する形が刺さらなかった理由が「間が空くこと」だった場合、
数時間待ちでも同じ結果になる。

ただし決定的な違いがある。**子どもが自分で注文する。**
親が仲介する形では、子どもは注文すらしていなかった。

だからこの実装が刺さらなかった場合、残る原因は「間」に絞られる。
そのときは同期生成へ倒す。切り分けとして設計されている。

## 判断 2: API キーは生成を回す場所だけに置く

アプリ（クライアント）にも Vercel にも Anthropic の API キーを置かない。

生成は GitHub Actions のスケジュール実行で回す。理由は 2 つ。

- **Vercel Cron は Hobby プランだと 1 日 1 回に制限される。** 数時間おきにできない
- **Vercel にルートを作らないので、守るべき口が増えない。** 生成を叩ける URL が存在しない

### Supabase の service_role キーは使わない

生成を回す側も、既存の RLS の枠内で動かす。
anon キー + 家族の合言葉（`x-family-code`）で、既存のテーブルと同じ分離に乗せる。

service_role キーは RLS を全部無視する。生成のために全権限の鍵を増やす理由がない。
Actions が持つのは「合言葉」と「anon キー」と「Anthropic の API キー」の 3 つだけ。

## 判断 3: テーブルは 1 つ。状態を列で持つ

注文と完成品を別のテーブルに分けない。分けると、
注文だけ残って完成品が無い状態、逆の状態、の両方を扱う羽目になる。

`stories` 1 つに `status` を持たせる。

| status | 意味 | 子どもの画面 |
| --- | --- | --- |
| `ordered` | 注文済み。まだ作られていない | 「つくってもらっているところ」 |
| `ready` | 生成・検査を通った | 遊べる |
| `failed` | 2 回試しても検査を通らなかった | 「うまく できなかったみたい」 |

## 判断 4: 生成物は必ず既存の検査を通す

`src/lib/story.ts` の `validateStory` が既にある。漢字、100 字超、
負けたときの話の欠落、枝ごとの数の不足、組み合わせ数の不足を弾く。

LLM の出力をそのまま信用しない。検査を通らなければ 1 回だけ作り直し、
それでも通らなければ `failed` にする。**壊れた話が子どもの画面に出ることはない。**

この検査は第 2 段階で「親が LLM に投げた結果を検査する」ために書いたものだが、
そのまま自動生成の安全弁として効く。

## 判断 5: 親の確認は事後

作ったらすぐ遊べる。親は後から一覧を見て消せる。

事前承認にしない理由は判断 1 と同じで、**即時性がこの仕組みの核**だから。
親が仲介する形が刺さらなかった可能性の筆頭が「間」である以上、
間を増やす方向の設計は採らない。

安全は 2 段で担保する。

1. 生成時の機械的な検査（漢字・文字数・こわい表現の禁止・語彙の制限）
2. 親画面からの事後の削除

## 判断 6: 未習の段の話は注文できない

注文するとき、段は解放済みのものから選ぶ。

設計メモの「未習の段を出すと『わからない』だけが残る」は、
子どもが自分で注文する場合も変わらない。むしろ自分で選んだ分、
分からなかったときの落差が大きい。

## 判断 7: 1 日の本数に上限を置く

子どもが連打しても費用が跳ねない形にする。

上限は 2 か所で効かせる。クライアント側（注文ボタンを止める）と、
処理側（1 回の実行で処理する件数の上限）。
クライアント側だけだと、合言葉を持っていれば直接 API を叩いて迂回できる。

## 検討して採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| アプリから同期で LLM を呼ぶ | 待ちを許容できるなら、キーを置く場所が 1 か所減る方を採る。ただし「間」が原因で刺さらなかった場合はこちらへ倒す |
| Vercel Cron で回す | Hobby プランだと 1 日 1 回。数時間おきにできない。Pro なら選択肢になる |
| service_role キーを生成側に置く | 既存の RLS の枠内（anon + 合言葉）で足りる。全権限の鍵を増やす理由がない |
| 生成なしの穴埋め式（子どもが直接セリフを埋める） | 「注文して作ってもらう」感が出ない。Gemini で遊んでいた様子と合わない。書く量も多い |
| 親が事前に確認してから公開する | 即時性が核。間を増やす方向は採らない |
| 注文と完成品でテーブルを分ける | 片方だけ存在する状態を扱う羽目になる |
| 生成を Supabase の Edge Function / pg_cron で回す | 動くが、Anthropic のキーを Supabase 側にも置くことになる。鍵の置き場所は 1 か所に寄せる |
| 失敗した話を黙って消す | 何が起きたか分からないまま注文が消える。`failed` として残し、親には理由を見せる |

## 未確定・次に決めること

- **スケジュールの間隔。** 数時間おきか、生活リズム（朝と夕方）に合わせるか。
  後者のほうが「届いている」感が出る可能性がある
- **失敗時の作り直し回数。** 今は 1 回で置いているが、実際の通過率を見て決める
- **1 日の上限本数。** 3 本程度から始める
- **届いたことをどう知らせるか。** プッシュ通知には依存しない（設計メモの方針）。
  アプリを開いたときに分かる印で足りるか、様子を見る
