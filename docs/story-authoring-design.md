# 九九バトル 第 4 段階 設計メモ — 子どもが話を注文する

`story-mode-design.md` の続き。ストーリーモードが使われなかった原因と、その直し方の記録。

採用した案と、検討して採らなかった案の両方を残す。理由まで書いておくことで、
後から同じ案を思いついたときに検討をやり直さずに済む。

## 発端

ストーリーモードは実装済み（2 エリア・各 720 通り）だが、実機で使われていない。
理由を本人に確認したところ、次のことが分かった。

> 娘は元々、AI にストーリーを作らせて、それを読むのを楽しんでいた。

つまり楽しんでいたのは **読むこと** ではなく **作らせること** だった。
読むのはその結果にすぎない。

### これは設計メモが既に言っていたことである

`story-mode-design.md` の冒頭にこう書いてある。

> **子どもが作った話が、ゲームになる。**
>
> 報酬は「話の続きが読めること」ではなく「自分の考えた世界が動いていること」。
> 前者はアプリ内に置いた報酬であり、後者は現実の達成である。**この区別が設計全体を分ける。**

そして実装されたのは、2 エリア・各 720 通りの **読むための話** である。
メモが「これではない」と名指しした側を作り込み、
「これである」と書いた側（子どもがアプリから話を追加する画面）を未実装のまま残していた。

720 通りへの拡張も同じ読み違いの上にある。実機で「1 回で遊び尽くされる」と報告を受け、
それをバリエーション不足と解釈して組み合わせを増やしたが、
1 回で終わったのは変化が足りなかったからではなく、**読むこと自体が動機ではなかった**から。

### 親が仲介する形は既に試して刺さらなかった

`story-prompt.md` は、親が LLM に投げて JSON を作り、手で置く手順である。
これは試されたが刺さらなかった。

**この形には、子どもが注文する瞬間が無い。** 子どもから見ると、
出てきた話が built-in の 2 エリアと区別がつかない。種を出した記憶と、
数日後に現れた話が結びつかない。

## 判断 1: 同期生成ではなく「注文 → あとで届く」にする

本人の提案。待ちが発生してよい代わりに、1 日に数回のスケジュール実行で作る。

採った理由は 3 つ。

**アプリ側に生成の口を作らなくて済む。** 注文を置くだけなら、
生成を叩ける URL が存在しない。守るべき口が増えない。

**作るのが人の手番になる。** 後述のとおり生成は親の Claude が行う。
同期生成にすると、その場で待たせるために API を呼ばざるを得なくなる。

**待つこと自体が体験になりうる。** 注文して、あとで届く。
設計メモの柱 4 は「そのアイデアが**翌日には動いている**状態にする」を想定しており、
数時間はその範囲内どころか、かなり速い側である。

### 残るリスクと、その切り分け

親が仲介する形が刺さらなかった理由が「間が空くこと」だった場合、
数時間待ちでも同じ結果になる。

ただし決定的な違いがある。**子どもが自分で注文する。**
親が仲介する形では、子どもは注文すらしていなかった。

だからこの実装が刺さらなかった場合、残る原因は「間」に絞られる。
そのときは同期生成へ倒す。切り分けとして設計されている。

## 判断 2: LLM を API として呼ばない

**Anthropic の API は従量課金である。** claude.ai のサブスクリプションとは別請求で、
Pro や Max に入っていても API 利用分はカバーされない。
子どもが注文するたびに課金が発生する仕組みは、この家庭用のアプリには重い。

そこで、**話を書くのは親の Claude 自身**にする。
スケジュールタスク（Routine）がこのリポジトリのセッションを起こし、
そのセッションが Supabase から注文を読み、話を書き、検査して、書き戻す。

| | API を呼ぶ案 | 採った案 |
| --- | --- | --- |
| 書き手 | Anthropic API | 実行している Claude 自身 |
| 費用 | 1 本あたり数十円の従量課金 | サブスクリプションの範囲 |
| 鍵 | Anthropic の API キーが要る | 要らない |
| 親の手動実行 | 別口で仕組みが要る | 同じ文面を投げるだけ |

手順は `docs/story-task.md`。アプリ側は注文を置くだけで、生成には一切関わらない。

### 台帳に答えが書いてあった

この家庭の自動化は既に Cowork のスケジュールタスクで回っている
（朝のニュース収集、知識定着チェック、メール仕分け）。
最初に API 前提で設計したのは、その実態を確かめなかったこちらの誤り。

### Supabase の service_role キーは使わない

生成を回す側も、既存の RLS の枠内で動かす。
anon キー + 家族の合言葉（`x-family-code`）で、既存のテーブルと同じ分離に乗せる。

service_role キーは RLS を全部無視する。生成のために全権限の鍵を増やす理由がない。
スクリプトが持つのは「合言葉」と「anon キー」の 2 つだけで、
どちらもアプリが既に持っているものと同じである。

#### 分離は負の側から実測する

anon キーは公開されるものなので、分離を担保しているのは RLS のポリシーだけである。
したがって「同期が成功した」ことは分離の証明にならない。確かめるべきは、
**通らないはずのものが通らないこと**である。

`stories` について、合言葉を 2 つ用意して次を実測した（2026-10-27）。

| 条件 | 結果 |
| --- | --- |
| 家庭 A の合言葉で見える行 | 1（自分の行だけ） |
| 家庭 B の合言葉で見える行 | 1（自分の行だけ） |
| 違う合言葉で見える行 | 0 |
| ヘッダ無しで見える行 | 0 |
| 違う合言葉で他家庭の行を update | 0 件 |
| 違う合言葉で他家庭の行を delete | 0 件 |

`stories` は `runs` と違って update と delete のポリシーを持つ。
読めないことだけ確かめて済ませると、書き込み側が空いていても気付けない。
下の 2 行がこの検証の本題である。

RLS の土台になる `public.request_family_code()` は `search_path = ''` で固定してある。
固定しないと、検索パスを差し替えて別の同名関数を呼ばせる余地が残る。

## 判断 3: テーブルは 1 つ。状態を列で持つ

注文と完成品を別のテーブルに分けない。分けると、
注文だけ残って完成品が無い状態、逆の状態、の両方を扱う羽目になる。

`stories` 1 つに `status` を持たせる。

| status | 意味 | 子どもの画面 |
| --- | --- | --- |
| `ordered` | 注文済み。まだ作られていない | 「つくってもらっているところ」 |
| `ready` | 生成・検査を通った | 遊べる |
| `failed` | 2 回試しても検査を通らなかった | 「うまく できなかったみたい」 |

## 判断 4: 生成物は必ず既存の検査を通す

`src/lib/story.ts` の `validateStory` が既にある。漢字、100 字超、
負けたときの話の欠落、枝ごとの数の不足、組み合わせ数の不足を弾く。

書き手の出力をそのまま信用しない。`publish` は検査に通らなければ書き込まない。

**読む側でも必ず検査する。** 手で直接 Supabase を触ることもできる以上、
公開済みの行が壊れている可能性は消えない。アプリは読み込んだ話を毎回検査し、
通らないものは遊べる一覧に出さず「うまく できなかったみたい」として見せる。
壊れた話が子どもの画面に出る経路を残さない。

この検査は第 2 段階で「親が LLM に投げた結果を検査する」ために書いたものだが、
そのまま自動生成の安全弁として効く。

## 判断 5: 親の確認は事後

作ったらすぐ遊べる。親は後から一覧を見て消せる。

事前承認にしない理由は判断 1 と同じで、**即時性がこの仕組みの核**だから。
親が仲介する形が刺さらなかった可能性の筆頭が「間」である以上、
間を増やす方向の設計は採らない。

安全は 2 段で担保する。

1. 生成時の機械的な検査（漢字・文字数・こわい表現の禁止・語彙の制限）
2. 親画面からの事後の削除

## 判断 6: 未習の段の話は注文できない

注文するとき、段は解放済みのものから選ぶ。

設計メモの「未習の段を出すと『わからない』だけが残る」は、
子どもが自分で注文する場合も変わらない。むしろ自分で選んだ分、
分からなかったときの落差が大きい。

## 判断 7: 1 日の本数に上限を置く

子どもが連打しても費用が跳ねない形にする。

上限は 2 か所で効かせる。クライアント側（注文ボタンを止める）と、
処理側（1 回の実行で処理する件数の上限）。
クライアント側だけだと、合言葉を持っていれば直接 API を叩いて迂回できる。

## 検討して採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| Anthropic の API を従量課金で使う | 子どもが注文するたびに課金される。家庭用のアプリでその構造は重い。親の Claude が書けば、サブスクリプションの範囲で済む |
| アプリから同期で LLM を呼ぶ | 待ちを許容できるなら API を使う理由が無くなる。ただし「間」が原因で刺さらなかった場合は再考する |
| GitHub Actions で回す | 動くが、Anthropic の API キーが要る。親の Claude のスケジュールタスクなら鍵が要らない |
| Vercel Cron で回す | 同上に加え、Hobby プランだと 1 日 1 回に制限される |
| service_role キーを生成側に置く | 既存の RLS の枠内（anon + 合言葉）で足りる。全権限の鍵を増やす理由がない |
| 生成なしの穴埋め式（子どもが直接セリフを埋める） | 「注文して作ってもらう」感が出ない。Gemini で遊んでいた様子と合わない。書く量も多い |
| 親が事前に確認してから公開する | 即時性が核。間を増やす方向は採らない |
| 注文と完成品でテーブルを分ける | 片方だけ存在する状態を扱う羽目になる |
| 生成を Supabase の Edge Function / pg_cron で回す | 同じく API キーが要る |
| 読む側の検査を省く（書き手が通したものを信じる） | Supabase は手でも触れる。信じる理由がない。検査は両側でかける |
| 失敗した話を黙って消す | 何が起きたか分からないまま注文が消える。`failed` として残し、親には理由を見せる |

## 未確定・次に決めること

- **スケジュールの間隔。** 既定は 7 時・12 時・18 時に置いた。
  生活リズムに合っているかは様子を見る
- **検査の通過率。** 何回書き直せば通るかは実際に回すまで分からない。
  よく落ちる項目が偏るなら `docs/story-prompt.md` 側を直す
- **1 日の上限本数。** 3 本から始める
- **届いたことをどう知らせるか。** プッシュ通知には依存しない（設計メモの方針）。
  アプリを開いたときに分かる印で足りるか、様子を見る
