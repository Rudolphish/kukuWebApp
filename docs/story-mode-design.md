# 九九バトル 第 2 段階 設計メモ — ストーリーモード

`design-notes.md` の続き。ナラティブ RPG としての進行を九九に重ねる案の記録。

**このメモは実装を約束するものではない。** 現時点で第 1 版の反応（親が言わずに開いたか）は
まだ観測できていない。土台が回っていない段階でこれを乗せると、
何が効いたのかが分からなくなる。判断の材料が揃うまで、ここは設計だけを溜める場所とする。

採用した案と、検討して採らなかった案の両方を残す。理由まで書いておくことで、
後から同じ議論を繰り返さずに済ませる。

## 発端

子どもが生成 AI と会話しながら物語を作って遊んでいた。

これは `design-notes.md` の柱 4「作る側に巻き込む」に対して、
**入口が既に開いている**ことを意味する。通常はまず「作る側に興味があるか」を確かめる必要があるが、
その確認は済んでいる。さらに、LLM と共同で作る習慣そのものが既にある。

新しい習慣を作るのではなく、既にある習慣にアプリを挿す形になる。これは有利な条件である。

## 中心となる考え

> **子どもが作った話が、ゲームになる。**

報酬は「話の続きが読めること」ではなく「自分の考えた世界が動いていること」。
前者はアプリ内に置いた報酬であり、後者は現実の達成である。この区別が設計全体を分ける。

## 全体の構造

### モードを分ける

タイムアタックとストーリーは同居させない。ホーム画面で選ばせる。

| モード | 内容 | 動機の源 |
| --- | --- | --- |
| タイムアタック | 現行の形。親子の非同期対戦 | 親の記録を抜くこと |
| ストーリー | 一人で進める | 自分の作った世界が動くこと |

RPG として進行させると「タイムを競う」動機は薄れる。
柱 2（親子の非同期対戦）とストーリーは動機の構造が違うため、無理に統合しない。

分けておけば、片方が刺さらなくても片方が残る。第 1 版を捨てずに済むことも大きい。

### 進行のループ

```
街  →  散策  →  遭遇  →  九九バトル(10問)  →  結果に関わらず話が進む  →  街
```

街に戻るところでループが閉じる。ここが設計上もっとも効く点である。
1 回の終わりが構造として定義されるため、「街に戻ったら今日はおしまい」が自然に作れる。

**街から次の散策へ自動で送らない。** 必ず能動的に選ばせる。
自動送りにした時点で、際限のない作りになる。

### エリアの解放

エリアが段に対応する。あるエリアで一定まで進むと次のエリアが解放され、次の段に挑戦できる。

これは `design-notes.md` の「進度の可視化として設計すれば健全」に該当する。
達成と無関係な配布ではないため、ガチャにはならない。

## 判断 1: 経験値を「習熟度」に読み替える

**この設計で唯一の地雷は経験値である。** 素直に実装すると原則を壊す。

| 経験値の増え方 | 何が起きるか |
| --- | --- |
| プレイ回数で増える | 時間を積むゲームになる。「長時間プレイを推奨しない」と衝突 |
| 正答数で増える | 間違いが実質的な減点になる。「間違いは減点しない」と衝突 |

どちらに倒しても原則を壊すため、経験値という概念そのものを置き換える。

> **見た目は経験値バー。中身は習熟度。**

判定には既存のデータをそのまま使える。`FactStat`（`attempts` / `wrong` / `avgMs`）を
その段の 9 問ぶん見て、「安定して速く答えられるか」で解放可否を決める。

- 回数を積んでも進まない（作業ゲーにならない）
- 間違えても減らない。減点ではなく「まだ安定していない」だけ
- 覚えたら進む。現実の達成と一致する

### 学校の進度との関係

習熟度で解放条件を満たしても、**実際に開けるのは親**とする。

条件を満たした時点で親画面に通知を出し、親が承認して初めてエリアが開く。
`design-notes.md` の「学校で今どこをやっているかに合わせるのが最優先」は変わらない。
先取りしすぎることを止められる形にしておく。

## 判断 2: ストーリーにデータベースは要らない

ストーリーは**読み取り専用・書き込みなし・利用者が一人**である。静的な JSON で足りる。

- Vercel から静的配信すれば Service Worker がキャッシュする。オフラインでも進められる
- データベースが必要なのは進行状況だけで、それは現行の localStorage で足りている
- 量が増えたらエリアごとに JSON を分割し、遅延読み込みすればよい

未検証の Supabase を土台に乗せずに作れる。設計を軽くできる。

なお、**記録と共有設定は Supabase へ移した**（親が自分の端末を使うため）。
この判断が指しているのはストーリーのデータであり、そちらは静的 JSON のままでよい。
読み取り専用で、利用者が一人で、書き込みが無いという性質は変わらない。

## 判断 3: 宣言的なスキーマにする。イベントコマンド列は作らない

データとエンジンを分け、内容を外部ファイルで足せるようにする発想は
RPG ツクール（MV / MZ 以降は JSON 形式）から借りる。現行の `themes.json` が既に小さくこれを行っている。

ただし**イベントコマンド列は借りない。**

ツクールのイベントの実体は命令列を歩くインタプリタである。
文章の表示、条件分岐、変数操作、ラベルジャンプを備えた小さなプログラミング言語と VM に近い。
これを実装すると、九九アプリではなく汎用ゲームエンジンを作ることになる。実害は 3 つある。

1. **型で守れない。** JSON に書いたロジックの誤りはコンパイラが検出できない
2. **LLM が壊す。** スキーマが深く分岐が多いほど、生成された JSON が不正になる確率が上がる。
   「子どもの語りを LLM で JSON 化する」という運用の要が不安定になる
3. **親が読めない。** 手で直せなくなった時点で、翌日反映のサイクルが死ぬ

代わりに、手続きではなくシーンそのものを記述する。

```json
{
  "id": "enc-slime-01",
  "enemy": "スライムキング",
  "intro": "くさむらが がさがさ うごいた。",
  "outroWin": "スライムは ぷるぷる にげていった。",
  "outroLose": "スライムは まんぞくそうに かえっていった。",
  "reward": "きんかい"
}
```

`outroWin` と `outroLose` を両方必須にする点が重要である。
**どちらに転んでも話が進むことが、スキーマのレベルで保証される。**
負けたときの話を書き忘れられない構造にしておく。

変数もフラグもラベルも持たない。進行度は数値 1 つ（`progress`）のみ。
分岐が必要なシーンにだけ `choices` を生やす。

この範囲であれば、型と起動時のバリデーションで守れ、LLM もまず壊さず、
親が読んで直せ、インタプリタも小さく収まる。
分岐が複雑になったら、その時に足せばよい。

## 判断 4: 街は縦の筋、散策は横の変化

遭遇が毎回ランダムだと、出来事の羅列になって「話」にならない。
物語を好む子どもは筋を見ている可能性が高い。

| パート | 性質 | 役割 |
| --- | --- | --- |
| 街 | 固定。進行度に応じて変化 | 縦の筋。NPC が進行に応じて違うことを言う |
| 散策 | ランダム | 横の変化。飽きへの対策 |

進行状態に `seenEncounters` を持ち、同じ遭遇が続けて出ないようにする。
現行の出題ロジックにある `avoidAdjacentRepeats` と同じ発想である。

## 話の流れの形（案）: ゲームブック

**これは決定ではなく案である。** 実装に入る前に、この形で書けるかを 1 本試してから決める。

話の流れと分岐を、ゲームブック（番号付きのパラグラフを選択肢でたどっていく形式）として捉える。

### なぜこの形が合うか

ゲームブックの構造は、判断 3 で決めた宣言的スキーマとほぼ同じものである。

| ゲームブック | このアプリ |
| --- | --- |
| 番号付きのパラグラフ | シーンのデータ |
| 「12 へ進め」 | 選択肢の行き先 |
| 持ち物・体力のわずかな管理 | 進行度の数値 1 つ |
| 紙の上で成立する | 親が手で読んで直せる |

ツクール式のイベントコマンド列を採らなかった判断が、ここで裏から支えられる。
ゲームブックには変数もラベルジャンプも要らない。パラグラフと行き先だけで話が成立する。

**紙で成立する形式である**ことが実務上いちばん効く。
親が手で書けて、LLM に投げるときも単位が明確で、子どもが口で言った内容もパラグラフに落としやすい。

### ただし、そのまま持ち込めない点が 3 つある

**1. ゲームブックは死ぬ。**
「冒険はここで終わった。最初からやり直せ」は減点そのものである。
`design-notes.md` の「間違いは減点しない」と正面から衝突する。

行き止まりを作らない。すべてのパラグラフに出口を持たせ、
出口のないパラグラフは**起動時のバリデーションで弾く**。
`outroWin` / `outroLose` を両方必須にしたのと同じ考え方で、
「行き止まりを書けない」ことをスキーマの側で保証する。

**2. ゲームブックは読み物である。**
1 パラグラフが 200〜400 字あるのが普通だが、小 2 には長すぎる。
音声で読み上げる前提の長さに制限する。**1 パラグラフ = 音声 30 秒以内、目安 100 字程度。**

**3. 番号は子どもに見せない。**
ゲームブックの番号は紙をめくるための仕組みであり、画面では要らない。
ただし作る側には有用なので、データ上は id として持ち、画面には出さない。

### 街をハブにしたグラフにする

判断 4（街は縦の筋、散策は横の変化）と両立する。

- **街** — グラフの入口であり出口。散策は必ずここへ戻る
- **散策** — パラグラフのグラフを数ノードたどって街へ帰る

1 回の散策を **3〜5 ノード**に収めれば、判断 5 の「1 ループ 3 分」も守れる。
グラフを深くしないことが、そのまま時間の歯止めになる。

### パラグラフの形（素案）

```json
{
  "id": "p-12",
  "text": "ふるい はしが かかっている。したは まっくらだ。",
  "battle": "enc-slime",
  "choices": [
    { "label": "はしを わたる", "to": "p-15" },
    { "label": "したへ おりる", "to": "p-18" }
  ]
}
```

- `battle` があれば、そのパラグラフで九九バトルが起きる。**勝敗は行き先を変えない**
  （判断済み。勝敗で分岐させると負けルートが罰になる）
- `choices` が無いパラグラフは街へ帰る終端として扱う
- どこへも行けず街にも帰らないパラグラフは、バリデーションでエラーにする

### 文章は LLM が書く。役割を分ける

パラグラフの文章を親が書くのではない。生成は LLM に任せ、事前生成して保存する。
実行時に LLM を呼ばないことは判断済み（応答速度と費用の両面）。

| 誰が | 何を |
| --- | --- |
| 子ども | 話の種を出す。敵の名前、世界観、「こういう話にして」 |
| LLM | 種をパラグラフのグラフとして文章化する |
| 親 | 生成結果を読んで確認し、リポジトリに置く |

親の作業は執筆ではなく**確認と設置**である。ここが実質的な運用コストになる。

### LLM に生成させるとき、守らせる制約

グラフは整合性が要るため、LLM が壊しやすい。
プロンプトで指示し、**起動時のバリデーションで機械的に検証する**。指示だけに頼らない。

- 選択肢の行き先 id が、すべて実在するパラグラフを指していること
- 出口のないパラグラフが無いこと（行き止まりを作らない）
- 1 パラグラフが目安 100 字以内であること
- ひらがな中心で、小 2 が知らない漢字を使わないこと
- 戦闘のあるパラグラフは `outroWin` と `outroLose` を両方持つこと
- 街から街まで 3〜5 ノードで帰れること

検証に落ちたら生成し直す。人が直すより速い。

### 生成に任せると、柱 4 が薄まる

**これがこの案の最大の懸念である。**

`design-notes.md` の柱 4 は「子どもがデザイナー、親が実装者」であり、
効き目の源は「自分の考えたものが動いている」という感覚にある。
話を LLM が考えてしまうと、動いているのは子どものものではなくなる。

したがって **LLM は文章化する道具であって、話を考える主体にしない。**
生成には必ず子どもが出した種を入れる。種が無いまま生成した話は、
既製のドリルと同じ立場になり、飽きるのも速い。

種は少量でよい。敵の名前 1 つ、「どこへ冒険に行くか」1 行でも、
それが入っていれば子どもにとっては自分の話になる。

### 確かめたいこと

- 子どもが出した種だけで、LLM が筋の通ったグラフを出せるか
- 生成したグラフがバリデーションを何割通るか。落ちるならプロンプトで直るのか
- 親が生成結果を確認して置くまでに何分かかるか。続けられる長さか
- 子どもが選択肢を「選ぶ」こと自体を面白がるか。それとも早くバトルに行きたがるか
- 同じグラフを 2 回目に通ったとき、違う選択肢を試すか

## 判断 5: 「1 回 1 分」は意識的に緩める

街から散策、バトル、話、街へ戻るまでを詰めても 2〜3 分はかかる。
バトル部分の「10 問 1 分」は守れるが、ループ全体は伸びる。

緩めること自体は許容する。ただし**無自覚に伸びるのが最も悪い**ため、
「1 ループ 3 分、1 日 1〜2 ループ」のように上限を先に決めて設計する。

街に戻る区切りと、次の散策を能動的に選ばせる仕様が、ここでの歯止めになる。

## 画面の設計

### 二段構成にする

上に絵の枠、下にメッセージ枠を置く、昔の RPG の形にする。
配色とフォントは第 1 版の `blocks` テーマをそのまま使い、ドット文字は使わない。
日本語のドットフォントはファイルが数 MB あり、初回の読み込みが重くなる。
普段読んでいる字でない、という理由もある。

### 読ませない原則とは衝突しない

`design-notes.md` が禁じているのは「文字だけの画面」であって、文字そのものではない。
絵があり、音声が流れ、文字が補助として出るなら原則の範囲に収まる。

条件は 1 つ。**読まないと進めない状態を作らないこと。**
音声だけで話が完結していれば、文字は読める子へのおまけでよい。

昔の RPG の文字送りは、この条件と相性がよい。
喋りに合わせて文字が出れば、読める子は目で追い、読めない子は耳だけで進む。
副作用として読字の練習になるが、それを画面に出して褒めない。

音声と文字送りを厳密に同期させることは狙わない。
`SpeechSynthesisUtterance` の `onboundary` は日本語で発火するかがブラウザ依存であり、
iOS Safari では期待できない。ずれても破綻しない作りにしておく。

### 送りは必ずタップで行う

自動送りにしない。理由は 3 つある。

1. 読むのが遅い子が置いていかれない
2. 押す行為が能動性を保つ。眺めるだけの時間を作らない
3. 街に戻るループと同じく、区切りが自分の手で入る

文字送りの途中でタップしたら一気に表示し、もう一度のタップで次へ進む。
音声の途中でタップされたら音声を止めて先へ進める。子どものペースを優先する。
画面のどこをタップしても進むようにし、▼ は「進めるよ」の合図としてだけ置く。

### 戦いに入る前に一拍おく

場面から戦闘へ、何の前触れもなく切り替わると話が途切れる。
敵が一歩ふみこむ → 絵の枠がひかる →「!」が跳ねる、を約 0.6 秒。
そのあと「バトル スタート！」を出して**止まり、タップで 1 問目に入る**。

「画面が切り替わった」ではなく「敵が動いたから戦いが始まった」という筋にする。
光は画面全体に広げず絵の枠の中に閉じる。夜に見ることを考えて、驚かせすぎない。

このタップは演出のためだけではない。
**指の準備ができる前に 1 問目が出ると、最初の 1 問だけ不利になる。**
スタートを自分で切れば、その不利が消える。
話を進めるタップと同じ作法なので、操作としても覚え直しが要らない。

演出の長さは 1 日に何度も見るものなので、これ以上は伸ばさない。

### 敵のセリフで、敵を採点する側から降ろす

戦闘前に敵があいさつし、正解・不正解のたびに短いひとことを返す。

> さいきん かけざん おぼえたんだ。あそぼうよ!

このひとことが構造を変える。
敵が九九のできる側として立ちはだかると、敵は採点する側になり、子どもは試される側になる。
敵じしんが覚えている最中で、間違えることもある、という立場にしておくと、
**子どもが間違えたときに責める主体が画面のどこにも居なくなる。**

したがって `onCorrect` より `onWrong` のセリフの方が効く。
褒め言葉を増やすより、敵が一緒に間違える方が強い。

- **すべての敵が「自分も間違える」と言う。** 1 体でも上から採点してくる敵がいると、そこだけ空気が変わる
- **敵ごとに語彙を変える。** 共通の語を使った瞬間にキャラクターが溶ける
- **複数から選び、直前と同じものは出さない。** 毎回同じだと空々しくなる

セリフはエンカウンターのデータとして持つ。敵の名前と同じく、最終的には子どもが書く。
「この敵はこう言う」を決めることは、名前を決めるより創作として大きい。

戦闘中のひとことに音声は付けない。1 問ごとに喋らせるとテンポが死ぬ。
読めなくても「敵が反応した」ことは伝わるので、文字は装飾の側に置く。

### 効果音は、選ぶ前に置き場所を決める

音そのものは後から選ぶ。先に決めるのは「どの瞬間に音が要るか」である。

| スロット | 鳴る場所 | 選ぶときの注意 |
| --- | --- | --- |
| おくり | 文字を送るタップ | 何百回も鳴る。耳に残る音は数日で嫌になる |
| そうぐう | 敵がふみこむ瞬間 | 緊張を作る側。ここでは解決させない |
| かいし | タップして戦いが始まる瞬間 | そうぐうを受けて解決する音にする |
| せいかい | 1 問あたる | 短く。次の問題を待たせない |
| まちがい | 間違えたとき | **ブザーにしない**（下記） |
| たおした | 全問あたって敵が倒れる | |
| かいほう | 次のエリアが開く | めったに鳴らないので長くてよい |

**まちがいの音だけは方針が固い。**
ブザーのような責める音を置くと、音で減点していることになる。
画面と文言でどれだけ「減点しない」を守っても、音が「ブブー」なら子どもはそちらを信じる。
低くやわらかい 1 音にする。

### 実装上、繰り返し踏んだこと

モックを直す過程で同じ種類の誤りを何度か踏んだ。実装時に同じ道を通らないよう残す。

- **重なりは寸法の調整で直さない。** セリフとキャラを別の段（フレックスの別要素）に分け、
  さらにキャラ側に `overflow: hidden` を掛ける。
  そうすれば計算を誤っても「小さく写る」で済み、重なりようがない。
- **キャラの大きさは画面幅ではなく、残った枠の高さから決める**（`cqh`）。
  縦の短い端末では問題文とキーパッドが場所を取って枠が潰れる。
  幅を基準にすると、そこでキャラだけが大きいまま残る。
- **絶対配置の要素には自分で位置を指定する。** 親フレックスの整列に頼っていると、
  親の `align-items` を変えた瞬間に位置が飛ぶ。
- **場面が変わってもキャラを動かさない。** メッセージ枠を消すと絵の枠が伸び、
  中央に置いたキャラが沈んで見える。動かすのはキーパッドが出る 1 回だけにする。
- **モックの端末は実寸で組み、入らないときは全体を `transform: scale()` で縮める。**
  枠だけを縮めて中身を実寸で残すと、実機では起きない潰れ方をして判断を誤らせる。

## 運用: 子どもの語りが翌日に動いている状態

この機能の成否は、**子どもが作り続けるかどうか**で決まる。

既製の話は 1 回で終わる。`design-notes.md` の「親が作ったものは飽きるのも速い」は
ストーリーでは特に厳しく効く。逆に、子どもが作り続ける形にできれば、
この機能は寿命問題そのものの解決策になる。

そのために、リポジトリに以下を置く。

- ストーリー JSON のスキーマ定義（TypeScript の型 + 起動時バリデーション）
- **親が LLM に投げるためのプロンプトテンプレート**

子どもが話したことをそのまま貼れば JSON が出てくる状態にしておく。
ここが整っていれば、柱 4 の「そのアイデアが翌日には動いている」が
親の手作業をほとんど挟まずに回る。この項目は地味だが、運用上もっとも重要である。

## 検討して採らなかった案

同じ議論を繰り返さないために、理由とともに残す。

| 案 | 採らない理由 |
| --- | --- |
| ストーリーの続きを報酬にする（クリアで続きが読める） | 構造がガチャと同じ。九九が話を読むための通行料になる。物語作りは既にある内発的な興味であり、それを九九の対価に変換すると、最も大事な興味が報酬目当ての作業に置き換わる |
| 勝敗でストーリーを分岐させる | 負けたルートが罰になる。「間違いは減点しない」と正面から衝突する。分岐させるなら子どもの選択で分岐させ、九九バトルは分岐条件ではなく話を進める場面として置く |
| 経験値をプレイ回数または正答数で増やす | 前者は時間を積むゲームに、後者は間違いの減点になる。習熟度への読み替えで解決する |
| ストーリーを Supabase に置く | 読み取り専用・利用者一人のデータに DB は不要。静的 JSON で足り、オフラインにも強い |
| RPG ツクール式のイベントコマンド列を実装する | 汎用ゲームエンジンの実装になる。型で守れず、LLM が壊し、親が直せなくなる |
| RPG ツクール自体を使う | PWA としてホーム画面に置く形と噛み合わない。音声読み上げと出題ロジックを作り直すことになる。Roblox を第 2 段階に置いたのと同じ理由で、学習コストを払う前に食いつくかを確かめたい |

## 未確定・確認が必要なこと

- 第 1 版で「親が言わずに開く」が起きるか。**これが観測できるまで実装に入らない**
- 1 ループの実測時間。3 分に収まるか
- 子どもが話を作り続けるか。1 本目を消費した後に 2 本目を持ってくるか
- 静的 JSON の分割単位。エリアごとで足りるか
- ゲームブック形式のグラフを LLM が壊さず出せるか。出せるなら分岐の形はそれに寄せる
- 習熟度の判定しきい値。どの程度で「安定して速い」と見なすか

## 実装するとしたら

反応を見てから、この順序で進める。

1. 分岐なしの直線ストーリー 1 本。街と散策とバトルのループだけ。
   画面はモックの構成をそのまま起こす（二段構成、文字送り、タップ送り、前触れとタップスタート、敵のセリフ）
2. 進行度に応じた街の NPC の変化
3. エリア解放と習熟度判定
4. 選択による分岐
5. 子どもの語りを JSON 化する運用の整備

1 の時点で乗ってこなければ、それ以降は作らない。
